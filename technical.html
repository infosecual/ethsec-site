How Argus works

Argus is EthSec's engine: a continuous-scanning, model-agnostic platform that finds and helps fix vulnerabilities in critical Ethereum code. This page is the engineering explanation, written for someone seeing the system for the first time.

It runs as three layers in one loop. el-bigote carries the methodology, the knowledge base, and the find-to-file loop. dobby runs open models on owned hardware for the high-volume reading and keeps a frontier model for the hardest reasoning. A dispatcher runs each unit of work in an isolated sandbox across many compute lanes at once.

Layer one

Orchestration, methodology, and knowledge: the find-to-file loop, a large library of analysis lenses, and 130+ tools that turn a target into ranked, validated findings.

Layer two

dobby

The local-model workhorse. Open models on owned hardware do the high-volume reading and emit typed, checkable results; a frontier model orchestrates and verifies. Breadth at near-zero marginal cost.

Layer one

el-bigote: orchestration, methodology, and knowledge

el-bigote is the security-review framework at the center of Argus. It holds the methodology, the knowledge base, and 130+ tools, and runs a single loop from a first lead to a filed report. It is model-agnostic: the same loop drives a frontier model, a local open model, or a deterministic analyzer, and routes each task to whichever is cheapest for the required reliability. A few mechanisms do most of the work.

Lead generation at scale

Many diverse analysis lenses run over a target, each looking for a different class of mistake. Before a lens reads a piece of code, a knowledge-base router loads only the vulnerability-class knowledge that code can actually trip (from text with kb-pick, from code structure with kb-router), inside a fixed token budget, so every pass is focused rather than a generic checklist. Architectural notes are consulted first, then the language-specific knowledge base. Leads are surfaced at low confidence on purpose (10 to 20 percent is enough), because recall at this stage matters more than precision: the gauntlet is what removes the noise.

The validation gauntlet

Every candidate is attacked before it is believed. It passes only if it survives each stage in turn, and most do not. The cost per stage rises as the population falls, so cheap refutation runs first and expensive proof runs last.

The gauntlet. Each stage removes candidates; the bar widths are illustrative of the attrition, not a measured yield. An impact class is promoted only when a deterministic oracle fires on the exploit and stays silent on a matched control, so a claim rests on a test, not an opinion.

Compounding memory

Three durable, machine-readable memories make each pass cheaper than the last. A refuted-memory store records every dead end and is consulted before any hunt, so a mechanism that has already been ruled out is never re-derived. A knowledge-triples store holds learned facts about targets. A lens-coverage store records which lenses and tools have run on which engagement, so the planner knows what is genuinely unreviewed rather than merely unread.

Choosing the next move

Work is ranked by one model: audit-work coverage multiplied by expected value, minus a dampening term from refuted memory. The planner reads a per-engagement coverage map (target repo plus exact code version, surfaces, a per-work-type coverage matrix) and picks the next action by expected dollars of avoided risk, with a small exploration bonus. Effort follows risk and unreviewed surface, not habit, and findings carry the exact tag or commit because coverage decays as code changes. Confirmed fixes are pushed down to forks (upstream-variant analysis) and leads are propagated sideways across variants.

Where the human sits

A model's verdict is a lead, never a confirmation. Only a senior researcher confirms a true positive and files it, and nothing ships on a model's say-so. That is a deliberate throughput choice as much as a safety one: the pipeline does the bulk read-and-triage so the scarce expert attention is spent only on what has already survived the gauntlet.

Layer two · the local tier

dobby: the local-model workhorse

dobby runs the high-volume reading on open models on owned hardware, so breadth costs almost nothing at the margin. It is a hybrid design (a frontier model orchestrates and verifies, a local open model does the bulk reading and triage) packaged two ways: a local-analyst service the orchestrator calls for each slice of work, and a model-comparison harness that measures every model before it is trusted. The local model is a lead generator, not an oracle: its output is untrusted, typed data that the orchestrator and the deterministic tooling check, and it has no authority to act.

1 · precomputed context

Call graphs, reachability, and taint flows are computed deterministically by el-bigote's slicer and context-pack tools, then rendered first in every prompt. Because that prefix is byte-stable, the inference engine reuses its KV cache and the expensive prefill is paid once across many questions on the same target.

2 · local read and triage

An open model on owned hardware reads the rendered context and the ranked code slice, explains the taint, and triages candidates. It never executes a tool; it only reads and writes text.

3 · typed envelope out

It returns schema-validated JSON: a typed envelope carrying the result, a confidence score, and provenance back to the lines it relied on. Malformed or unparseable output is rejected and retried, never guessed at.

4 · orchestrator review

A frontier model plans the work and reads the compact JSON, spot-checking only the highest-severity claims against the real source. An adversarial refute pass then tries to disprove each survivor; majority vote, fail-open so a broken judge cannot silently drop a real bug.

5 · deterministic verification

Survivors enter el-bigote's gauntlet (reachability, differential testing, the oracle gate) and a senior researcher verifies and files. Nothing reaches a report on the local model's word alone.

Every outcome feeds back: an online reward store updates which model to route a given slice to, and a model-comparison harness scores each model against deterministic gold labels and real confirmed findings. Routing follows measured skill, not a public leaderboard.

The dobby pipeline. The local tier does the volume; the frontier tier and the deterministic tooling do the judging.

Measured, not assumed

Standalone vulnerability-detection skill is close to random across every model, so dobby measures rather than assumes. The harness runs the same security-reading task through N models (local and frontier) and scores them on a two-sided benchmark: recall (real bugs caught) and the false-affirm rate (how often a model confidently calls safe code vulnerable). Both matter, because a model that flags everything has perfect recall and is useless. Models are routed on that measured recall-versus-cost curve, per task type, and re-scored as they change.

Specialized, in progress

The open models are being fine-tuned with lightweight LoRA adapters on EthSec's own Ethereum-security corpus: past engagements and confirmed findings, the refuted-memory of dead ends, the lens and knowledge-base library, and the ecosystem's real Go, Solidity, and Rust code. Progress is judged on the same two-sided benchmark, because skill on C and C++ test sets does not read across to Cosmos-SDK Go or DeFi Solidity. As the open models prove out on owned hardware, the compute budget shifts toward them and away from metered frontier tokens.

Why local at all

Three reasons. Cost: the bulk read-and-triage is the largest token line, and moving it onto owned rigs makes breadth nearly free at the margin. Custody: source and in-progress findings for the bulk tier stay on the machine. Control: an open model can be measured, fine-tuned, abliterated, and pinned to an exact weight, so its behavior is reproducible rather than changing underneath the work.

Layer three

The compute and isolation layer

Read top to bottom as one unit of work. Compute lanes supply capacity; the control plane assigns a unit to a lane and a sandbox; each sandbox runs wf-run against one target with exactly one credential; findings are harvested through dedup and attribution. The services on the lower rail wrap every unit. Status tags mark what is built, in progress, or planned.

The design keeps one invariant at every scale: a credential is mounted read-only into exactly one sandbox, is confirmed to be the expected account before any work, and never appears in a command line or reaches the open network. Each unit runs wf-run against a single target pinned to a commit, behind an egress proxy that allows only an allowlist, so a prompt-injected target cannot exfiltrate or act. Many such units run at once, one per account.

  1. Credential-blind spine

    Built · 31 tests

    the part everything else sits on

    • Lanes registry with a no-secrets guard: metadata only, refuses any token value or secret-named field; a credential never lives here.
    • Impact-first scheduler: the queue is ranked by impact_priority (highs and crits coverage of the Argus scope); a bounty is a flag, never the ranker.
    • Best-ROI lane pick: local rig, then donated credits, then hosted model access, then a team environment, then metered API; cyber-use and opt-in gates; one active unit per account.
    • Hardened launch builder: generates the docker run and wf-run commands; refuses forbidden mounts; never puts a key in the argv. The security contract is asserted on the argv, so it holds without Docker.
    • Usage gate, locks, contained harvester: per-lane window gate from in-band signals, per-account concurrency locks, and a harvester that copies out into the engagement tree and never files.

  2. Real execute + two-account liveness

    Next

    prove isolation before any scale

    • Nine-stage launch-and-reap lifecycle: plan, prep (clone at pin), net (internal network + egress sidecar), acquire (lock), run, identity receipt, work (wf-run with heartbeat and journal sync), harvest, reap. Always reaps; resumes via wf-run --resume.
    • Identity guard: confirm the mounted login is the expected account before any work, without printing the token; a mismatch aborts.
    • Two-account liveness test: two isolated logins run concurrently on a trivial public target and must pass every row: concurrency, identity isolation, no token leak, no refresh-token collision, per-account window, kill-and-resume, clean reap.
    • Minimal kill-switch (stop-compute, stop-spill) and a dead-man lease so a lost control plane pauses rather than runs.

  3. Temporal control plane

    Planned

    durable, resumable, many at once

    • AccountLedger (one long-lived workflow per account): the slot gate holding live window state, concurrency, and the spill rule, replacing the single-shot usage gate.
    • UnitWorkflow (one per unit): reserve a slot, provision a sandbox, run the lifecycle with heartbeats, harvest, release; crash-resume from the journal plus Temporal history.

  4. Coordination across researchers

    Planned

    no wasted work, no duplicate filings

    • Claim board: lease a (target, surface, lens) so the fleet does not cover one surface fifty times, with an ensemble class for deliberate confidence and time-boxed leases against hoarding.
    • Cross-node dedup gate: cluster candidates by root cause before anything is filed, lock each cluster to one researcher; duplicates are unpayable and noisy to maintainers.
    • Attribution ledger: signed, append-only events for lease, spend, candidate, verification, filing, outcome; the source of truth for credit.
    • Program policy registry: per-program rules as a hard gate (one accountable human, AI disclosure where required, the filer reproduces the PoC), with a scope-drift watcher.
    Extends el-bigote coord.py; filing stays decentralized, each researcher under their own identity.

  5. Capacity allocator and telemetry

    Planned

    keep the whole fleet busy on the best work

    • Impact ordering in ev-planner: wire the impact rank and a coverage term so the allocator spreads across the 80+ targets; cost is not a gate (donated credits and the partnership).

  6. Trust hardening and scale-out

    Planned

    from a few accounts to the fleet

    • microVM per unit and a credential-free PoC VM: for handed-over or hostile-code units, so a prompt-injected target cannot reach the credential while proving a bug.
    • Anti-poisoning of shared memories: per-node signing, advisory kills, canary re-derivation, so one malicious node cannot hide a bug from the fleet.
    • Cloud SandboxProvider (E2B or Modal) and the v2 wf-run cross-account diff so one run can span accounts.
    • Node signing and workload identity (Sigstore, SPIFFE), and a minimal researcher console (node state, window, pause, their claims and verification queue).
    Enters only after the liveness test and an early yield read justify scaling.

The gate

Every scale-up is earned by a measured number

EthSec is a non-profit lab working in partnership with major model providers, so the binding constraints are security and quality, not budget: protecting embargoed findings, deduplication across researchers, the false-positive rate reaching a human, and bounded loss when the operator is offline. The goal is highs and criticals found and fixed across the whole Argus scope, filed where a bounty exists. Scale follows evidence, so the pilot graduates only when the numbers below hold.

verified-TP / unitReal confirmed findings per unit of work, the core yield signal.
dup-collision rateHow often two researchers file the same root cause. Must stay low to scale the fleet.
false-positive rateNoise reaching a human verifier. The number that protects expert attention.

Two more gate the operational risk: the re-authentication cadence per account, and the kill-drill time-to-silence (how fast a layered kill-switch stops compute, filing, and spill when the operator is offline). Steps 3 through 6 on the Roadmap enter only as these hold. Nothing scales on the plan alone; the two-account liveness test in step 2 is the first hard gate, and the rest follow the same rule.
